# 04 · Work 模式实战 —— 严格执行 plan，绝不另起 plan

> Work 模式的唯一输入是 **approved 状态的 plan 文档**。你是一个执行者，不是设计师。

## 启动 Work 模式

1. 应用里选中 **⚡ Work Mode** 卡片（绑定执行模型）
2. ▶️ Open in terminal → 直接运行 `claude`（默认权限，可写文件、跑命令）

## Work 会话开场提示词（复制即用）

```text
你是本项目的执行工程师，现在是 Work 模式。严格按以下 plan 文档执行：

    docs/plans/NNN-<主题>.md    （状态: approved）

铁律：
1. 只执行文档"任务拆解"里列出的任务，按顺序逐项完成
2. 不新增任务、不修改方案、不引入文档未列出的依赖或文件结构变更
3. 发现 plan 有错误、缺口或不可行时：立即停止执行并报告，
   等待 plan 修订后再继续——绝不现场自行设计替代方案
4. 每完成一个任务，把文档里对应的 [ ] 勾选为 [x]
5. 全部任务完成后，逐条核对"验收标准"并汇报结果

现在从 T1 开始。
```

## 执行纪律（为什么这么严）

| 铁律 | 防的是什么 |
| --- | --- |
| 只做任务清单里的事 | 执行模型"顺手重构 / 顺手优化"导致范围失控 |
| 不改方案、不换依赖 | 同一个功能两个模型各自理解，代码风格与架构割裂 |
| 发现问题就停，回去改 plan | 执行模型现场拍板的"更好方案"没人审过，是事故最大来源 |
| 逐项勾选更新文档 | 中断后新会话读文档即可精确续做，不重做不漏做 |
| 最后对照验收标准 | "做完了"≠"做对了"，验收标准是客观裁判 |

## 发现 plan 有缺口时（标准回路）

```
Work 执行中撞上 plan 未覆盖的情况
        │
        ▼
立即停止，输出：撞上了什么 / 为什么 plan 覆盖不了 / 建议回 Plan 修订哪些条目
        │
        ▼
切换 Plan 终端（claude-plan）→ 修订 docs/plans/NNN-….md → 人工 re-approve
        │
        ▼
回到 Work 终端：@docs/plans/NNN-….md 已更新，从任务 X 继续
```

**绝不**在 Work 会话里说"算了你直接改吧"——那等于放弃了整个双模式分工。

## 中断恢复

Work 会话崩了/关了没关系：新开会话用同样的开场提示词，模型读 plan 文档的勾选状态，从第一个未勾选任务继续。

## 完成标志

- 任务拆解全部 `[x]`
- 验收标准逐条核对通过并汇报
- 把 plan 文档状态改为 `done`

端到端全流程示例见 [05 章](05-workflow-example.md)。
