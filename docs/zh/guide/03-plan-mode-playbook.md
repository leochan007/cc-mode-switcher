# 03 · Plan 模式实战 —— 生成 plan 文档（中间产物）

> Plan 模式的唯一产出物是**一份可执行的 plan 文档**。不写业务代码、不做任何实现。

## 为什么需要 plan 文档

没有中间产物时，"计划"只存在于会话的上下文里：会话一关就没了，换模型/换会话就失真，执行时模型还会即兴发挥。把计划**物化成文档**后：

- 它成为 Work 模式的**唯一事实来源**（single source of truth）
- 人可以 review、修改、审批之后再放行
- Work 会话崩溃/中断后，新会话读同一份文档可以无缝续做
- Plan 和 Work 用的模型可以各自最优化（见 [02 章](02-models-and-providers.md#模型分工建议)）

## 启动 Plan 模式

1. 应用里选中 **🧠 Plan Mode** 卡片（绑定推理模型）
2. ▶️ Open in terminal → 输入 `claude-plan`
3. 等效于 `claude --permission-mode plan` + `MAX_THINKING_TOKENS=16000`（thinking 开启）

Plan 权限模式下 Claude Code 本身就是**只读**的——正好从机制上保证了"只出方案不动代码"。

## plan 文档约定

- 存放目录：项目根 `docs/plans/`
- 命名：`NNN-<短横线主题>.md`（如 `001-export-import-configs.md`），编号递增
- 一份 plan 一个主题，不贪大

## plan 文档标准模板

```markdown
# Plan: <一句话主题>

- 状态: draft | approved | in-progress | done
- 作者: claude-plan (<模型ID>) @ <日期>
- 关联: <需求来源/issue 链接>

## 1. 背景与目标
为什么做这件事；完成后应达成什么可验证的状态。

## 2. 现状分析
相关代码/模块的位置与行为；关键约束（框架版本、平台、性能、兼容性）。

## 3. 方案
选定方案及理由；列出被否掉的备选方案与原因（防止 Work 模式重新发明）。

## 4. 任务拆解
逐项可独立验证的最小任务，按依赖顺序排列。

- [ ] T1: <做什么> — 涉及文件: <paths>
- [ ] T2: <做什么> — 涉及文件: <paths>

## 5. 明确不做的事（Out of Scope）
本次不处理的相邻问题，防止范围蔓延。

## 6. 验收标准
- [ ] <可观察、可验证的条目>

## 7. 风险与回滚
可能出错的点及出现时的回退方式。
```

## Plan 会话开场提示词（复制即用）

```text
你是本项目的架构师，现在是 Plan 模式，你的唯一产出是一份 plan 文档，不要写任何实现代码。

需求：<把需求说清楚，越具体越好>

请先阅读相关代码（src/…、配置、依赖），然后按以下结构输出 plan 文档，
写入 docs/plans/NNN-<主题>.md（NNN 取目录里最大编号+1）：
背景与目标 / 现状分析 / 方案（含被否备选）/ 任务拆解（每项独立可验证，标注涉及文件）/
明确不做的事 / 验收标准 / 风险与回滚。

要求：
- 任务粒度：每个任务 Work 模式一次会话可完成并可单独验证
- 方案要具体到模块和函数级别，但不要贴大段实现代码
- 有不确定的地方在文档里标注 OPEN QUESTION，不要自行假设
```

## Plan 模式纪律

| 规则 | 原因 |
| --- | --- |
| 只产出/修订 plan 文档，不写业务代码 | 权限模式已强制只读，思想上也要遵守 |
| 不确定的写 OPEN QUESTION，不猜 | 猜出来的 plan 会把错误放大到执行阶段 |
| 每个任务标注涉及文件 | Work 模式可以直接定位，减少自由发挥空间 |
| 任务要"独立可验证" | 无法验证的任务等于没有完成标准 |
| 明确写 Out of Scope | 堵住 Work 模式"顺手多做一点"的口子 |

## 完成标志

plan 文档齐备（无 OPEN QUESTION 或已全部解决）→ **人工 review** → 把状态改为 `approved` → 才允许进入 [Work 模式](04-work-mode-playbook.md)。
